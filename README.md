# SSO — OAuth2 Provider API Reference

The Odoo `sso` module turns Odoo into an **OAuth2 Provider (authorization server)**,
built on Odoo's own `res.users` account system, and provides standard
**Authorization Code Flow** single sign-on (SSO) capabilities for third-party
applications. This module **does not integrate with any third-party IdP**; all
authentication is completed within Odoo.

- Version: 19.0.1.0.0
- Dependencies: `base`, `web`
- Grant type: `authorization_code` (with Refresh Token support)

---

## 1. Prerequisites (configure in the Odoo backend)

1. Log in as a system administrator and go to **SSO → SSO Applications → Create**.
2. Record the system-generated **Client ID** (`client_id`) and **Client Secret**
   (shown in plaintext only once, at creation or regeneration).
3. In **Redirect URIs**, enter the callback URL(s) of the third-party application
   (multiple values allowed, must match exactly).
   - The address that the logout endpoint (see `GET /sso/oauth2/logout`) redirects
     back to **must also** be in the allowlist; otherwise it falls back to the
     Odoo login page.
4. Key fields:
   - **Scope**: space-separated scopes, default `openid profile`.
   - **Access Token Validity (seconds)**: Access Token lifetime, default `3600` (1 hour).
   - **Refresh Token Validity (seconds)**: Refresh Token lifetime, default `86400` (24 hours).
   - **Approval Prompt**: `force` (always ask the user to confirm) / `auto` (skip the
     confirmation page automatically for returning users).
   - **Consent Expiry (days)**: how long the authorization consent is remembered; `0`
     means it never expires.

---

## 2. Endpoint Overview

| Method | Path | Auth | CSRF | Description |
|--------|------|------|------|-------------|
| GET | `/sso/oauth2/authorize` | `user` (login required) | required | Display the authorization consent page (browser flow) |
| POST | `/sso/oauth2/authorize` | `user` (login required) | required | User confirms / denies authorization (browser flow) |
| POST | `/sso/oauth2/token` | `none` | no | Exchange authorization code for token / refresh with Refresh Token |
| GET | `/sso/oauth2/userinfo` | `none` (Bearer Token) | no | Retrieve information of the logged-in user |
| GET | `/sso/oauth2/logout` | `user` (login required) | no | Destroy the Odoo SSO session and redirect |

> All path prefixes are relative to the Odoo service address, e.g.
> `http://127.0.0.1:8069/sso/oauth2/...`.

---

## 3. Detailed Endpoint Reference

### 3.1 GET `/sso/oauth2/authorize`

Displays the authorization page. **This endpoint is intended for browser
redirects** and should not be called directly from a server.

**Query parameters:**

| Parameter | Required | Description |
|-----------|----------|-------------|
| `client_id` | yes | The application's Client ID |
| `redirect_uri` | yes | Must exactly match the application's allowlist |
| `response_type` | yes | Fixed to `code` |
| `state` | yes | Random string generated by the client, used for CSRF protection; returned as-is via the callback |
| `scope` | no | Requested scopes; falls back to the application's configured value if omitted |

**Behavior:**
- Missing parameters or `response_type != code` → returns an error page.
- `client_id` / `redirect_uri` validation failure → returns an error page.
- `Approval Prompt = auto` and the user already has a valid consent record →
  generate the authorization code and redirect directly, **skipping the consent page**.
- Otherwise render the authorization consent page (with CSRF Token).

---

### 3.2 POST `/sso/oauth2/authorize`

Submitted when the user clicks "Authorize / Deny". **Browser form submission,
must include the CSRF Token.**

**Form fields:**

| Field | Description |
|-------|-------------|
| `csrf_token` | Odoo form CSRF token (pre-filled on the page) |
| `action` | `confirm` (authorize) or `deny` (deny) |
| `client_id` / `redirect_uri` / `state` / `scope` | Same as the GET request, returned via hidden fields on the page |

**Behavior:**
- `action = deny` → 302 redirect to `redirect_uri?error=access_denied&state=...`.
- `action = confirm` →
  - If `Approval Prompt = auto`, record the user's consent (`sso.user.consent`).
  - Generate an authorization code (5-minute lifetime, single-use), and 302
    redirect to `redirect_uri?code=...&state=...`.

> The authorization code corresponds to `sso.auth.code`; it is valid for 5 minutes
> and is invalidated immediately after a single use.

---

### 3.3 POST `/sso/oauth2/token`

**Client-credential (back-channel) call**, does not require a user login; used to
exchange or refresh a Token.

**Client authentication (choose one):**
- HTTP Basic Auth: `Authorization: Basic base64(client_id:client_secret)`
- Form fields: `client_id` + `client_secret`

#### 3.3.1 Exchange authorization code for Token — `grant_type=authorization_code`

**Request fields:**

| Field | Required | Description |
|-------|----------|-------------|
| `grant_type` | yes | `authorization_code` |
| `code` | yes | The authorization code obtained from the callback |
| `redirect_uri` | yes | Must match the one used when requesting the code |
| `client_id` | conditional | Required when Basic Auth is omitted |
| `client_secret` | conditional | Required when Basic Auth is omitted |

**Success response (200, application/json):**

```json
{
  "access_token": "at_xxxx",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "rt_xxxx",
  "scope": "openid profile"
}
```

#### 3.3.2 Refresh Token — `grant_type=refresh_token`

**Request fields:**

| Field | Required | Description |
|-------|----------|-------------|
| `grant_type` | yes | `refresh_token` |
| `refresh_token` | yes | A previously obtained Refresh Token |
| `client_id` | conditional | Required when Basic Auth is omitted |
| `client_secret` | conditional | Required when Basic Auth is omitted |

**Success response (200):** Same as 3.3.1, returns a **new** `access_token` and
`refresh_token`; the old Refresh Token is invalidated.

**Error response (400):**

```json
{ "error": "invalid_grant", "error_description": "..." }
```

Common `error` values: `invalid_client`, `invalid_request`, `invalid_grant`,
`unsupported_grant_type`.

---

### 3.4 GET `/sso/oauth2/userinfo`

Retrieve user information using the Access Token. **Back-channel call.**

**Request header:**

```
Authorization: Bearer <access_token>
```

**Success response (200, application/json):**

```json
{
  "sub": "7",
  "name": "Mitchell Admin",
  "login": "admin",
  "email": "admin@example.com",
  "user_id": 7,
  "partner_id": 10,
  "company_id": 1,
  "company_name": "My Company",
  "groups": [
    { "id": 1, "name": "Settings / Administrator", "xml_id": "base.group_system" },
    { "id": 9, "name": "User / Internal User", "xml_id": "base.group_user" }
  ]
}
```

**Error response (400):**

```json
{ "error": "invalid_token", "error_description": "Invalid or expired access token" }
```

> Token validation rules: it must exist, not be revoked (`revoked=False`), and not
> be expired (`expires_at > now`).

---

### 3.5 GET `/sso/oauth2/logout`

Destroy the Odoo SSO session and redirect. **Requires the user to be logged in
(browser flow).**

**Query parameters:**

| Parameter | Required | Description |
|-----------|----------|-------------|
| `redirect_uri` | no | Address to redirect to after logout, defaults to `/web`. **Must be within the
application's callback allowlist**, otherwise it falls back to `/web` (the Odoo login page) |

**Behavior:** Clears the Odoo session (`request.session.logout()`) and 302
redirects to `redirect_uri`.

---

## 4. Complete Flow (Authorization Code Flow)

```
Third-party app                 User browser                 Odoo SSO
   |                               |                            |
   | 1. User clicks "Log in"       |                            |
   |------------------------------>|                            |
   |                               | 2. GET /authorize          |
   |                               |    ?client_id&redirect_uri |
   |                               |    &response_type=code     |
   |                               |    &state=xxx              |
   |                               |--------------------------->|
   |                               | 3. [consent/login page]    |
   |                               |<-------------------------->|
   |                               | 4. POST /authorize         |
   |                               |    action=confirm&csrf...  |
   |                               |--------------------------->|
   |                               | 5. 302 redirect_uri        |
   |                               |    ?code=yyy&state=xxx     |
   |                               |<---------------------------|
   | 6. GET /callback?code=yyy     |                            |
   |<------------------------------|                            |
   |                               |                            |
   | 7. POST /token (code) --------|--------------------------->|
   |<---- {access_token, rt} ------|                            |
   |                               |                            |
   | 8. GET /userinfo (Bearer) --->|--------------------------->|
   |<---- {user info} -------------|                            |
   |                               |                            |
   | 9. Display user, create       |                            |
   |    local session              |                            |
```

- Steps 2–5 are **front-channel** redirects, performed by the browser.
- Steps 7–8 are **back-channel**, called directly by the third-party app's server
  to Odoo, invisible to the browser.
- `state` is generated in step 2 and verified in step 6, used for CSRF protection.

## 5. curl Examples

### Exchange Token (authorization code grant)

```bash
curl -X POST http://127.0.0.1:8069/sso/oauth2/token \
  -u "<client_id>:<client_secret>" \
  -d "grant_type=authorization_code" \
  -d "code=<AUTH_CODE>" \
  -d "redirect_uri=http://127.0.0.1:5000/callback"
```

### Refresh Token

```bash
curl -X POST http://127.0.0.1:8069/sso/oauth2/token \
  -u "<client_id>:<client_secret>" \
  -d "grant_type=refresh_token" \
  -d "refresh_token=<REFRESH_TOKEN>"
```

### Get User Information

```bash
curl http://127.0.0.1:8069/sso/oauth2/userinfo \
  -H "Authorization: Bearer <ACCESS_TOKEN>"
```

## 6. Scopes

In the current implementation, `scope` is recorded and passed through with the
Token / authorization code, and userinfo always returns the complete basic profile
(`sub`, `name`, `login`, `email`, `user_id`, `partner_id`, `company_id`,
`company_name`, plus the user's Odoo groups `groups`). Each item in `groups`
contains:
- `id`: the group record ID
- `name`: the group's full name (`full_name`)
- `xml_id`: the group's external technical identifier (e.g. `base.group_system`);
  empty string when no external ID exists

Clients may map permissions based on `xml_id`, since names may be translated or renamed.
The default scope is `openid profile`, and can be extended to space-separated custom
values in the application configuration as needed.

---

## 7. Security Notes

- **Authorization code**: 5-minute lifetime, single-use; verifies consistency of
  `client_id` and `redirect_uri`.
- **Client Secret**: stored as a SHA-256 hash; plaintext is shown only once at
  creation or regeneration.
- **Access Token**: expires after 1 hour by default; can be revoked individually
  (the Revoked flag on `sso.access.token`).
- **CSRF**: the GET/POST of `/authorize` are browser flows and POST requires a CSRF
  Token; `/token` and `/userinfo` use `auth='none'` and `csrf=False`, relying on
  Bearer Token / Basic Auth for protection.
- All authentication events are recorded in the `sso.log` audit log.
